# 0029. 実利用（RUM）のベースラインは件数がたまってから取り、Phase 1 は計測の土台ができたことで閉じる

- 状態: 採用
- オーナーの確認: 2026-10-04
- 日付: 2026-10-04
- 関連: ADR 0011 / 0012 / 0021 / 0023 / 0025 / 0028

## 背景

ロードマップの順番の考え方 2 は「変える前に測る」で、Phase 1 の DoD に「`docs/analytics.md` と `docs/performance.md` に、1 週間分のベースラインがある」がある（ADR 0011 / 0012 / 0021 の DoD も同じ）。v1.2.1 を本番に出した 2026-09-28 から 1 週間（2026-10-05）で、実利用のベースラインを書く予定だった。

ところが、本番にはほとんどアクセスがない。Vercel Web Analytics（CLI の `vercel metrics`）で 2026-09-20〜10-04 の本番の閲覧を見た。

| 項目 | 値 |
|---|---|
| ページの閲覧 | 36 回（デスクトップ 32・モバイル 4） |
| 日ごと | 2026-09-27 に 26 回（v1.2.0 / 1.2.1 を出した日のオーナーの確認）。ほかの日は 0〜3 回 |
| 参照元 | なし 28・vercel.com 6（ダッシュボードから開いたもの）・bing.com 2 |

外部の利用者と言えそうなのは、検索からの 2 回ほどしかない。このままでは、次の理由で実利用のベースラインとして使えない。

- **件数が足りない。** p75 は件数が少ないと大きくぶれる。100 件でも、p75 の 95% 信頼区間は、下から 66〜84% の位置まで広がる。数件では、ほぼ 1 回の値になる。
- **偏っている。** ほとんどがオーナー自身のアクセスで、速い回線と端末から、流れを知っている人が操作したもの。
- **オーナーのアクセスを後から除けない。** PostHog に送る ID はページを開くたびに変わり（ADR 0021 決定 6）、位置情報は国だけ（ADR 0020）なので、誰のアクセスかを見分けられない。

待っても、改善を本番に出すまで「変える前」の実利用のデータは増えない。一方、改善（ADR 0004・0005・0015・0022〜0028 など）は `develop` にたまっていて、本番に出ていない。

## 検討した選択肢

| 案 | 良い点 | 悪い点 |
|---|---|---|
| A. 2026-10-05 に、いまのデータでベースラインを書く | 予定どおり | 実際の利用者の値ではない。あとで比べると、誤った結論を出しうる |
| B. 件数の基準を決め、満たすまでリリースを待つ | 「変える前」の実利用のデータが取れる | いつたまるか分からない。改善が本番に出ないまま止まる |
| **C. Phase 1 は計測の土台ができたことで閉じ、「変える前」はラボの値で代える。実利用の値は件数がたまってから書く。リリースは待たない** | 改善を本番に出せる。誤った実利用の値を書かない | 「変える前」の実利用のデータは取れない（ただし、もともと取れる量がない） |

## 決定

1. **Phase 1 の「1 週間分のベースライン」は、件数が足りないため、計測の土台ができたことで満たしたとする。** 満たしたとするのは、イベントと `web_vital` が本番から PostHog に届いていること（2026-09-28 に確かめた）と、件数の見方（決定 3）を決めたこと。`docs/analytics.md` と `docs/performance.md` には、件数が足りないことと、その日付の件数を書く。
2. **「変える前」の比較の相手は、ラボの値にする。** リリースの前に、本番の版（`main`。v1.2.1）を、いまの CI の条件（ADR 0025 / 0028。温める 2 回を捨て、倍率を benchmarkIndex 440 に補正し、Sentry 有効で 7 回の指標ごとの中央値）で測り、`docs/performance.md` に「変える前」として書く。Phase 6 の効果の検証では、まずこのラボの値と比べる。
3. **実利用の値（p75）は、件数の基準を満たしてから書く。** 基準は、端末（モバイル / デスクトップ）ごとに、LCP の `web_vital` が 100 件。満たした端末から、`docs/performance.md` に LCP / INP / CLS の p75 を、`docs/analytics.md` に KPI を書き、ADR 0025 決定 3 の比較（基準の端末が甘すぎないか・厳しすぎないか）を行う。件数は、週に 1 回、PostHog（または Vercel Web Analytics の閲覧数）で見る。
4. **リリースは待たない。** 決定 2 を済ませたら、`release/*` で本番に出す（リリースの前にオーナーの確認を取る）。
5. **オーナー自身のアクセスは、件数から除けない前提で数える。** 本番での確認はリリースのときなどに限り、件数の基準は、オーナーのアクセスが混ざっていても足りる程度の多さにしている。

## 結果

- 良い点: 誤った実利用の値を書かずに、Phase 1 を閉じて改善を本番に出せる。「変える前」と「変えたあと」を、同じ条件のラボの値で比べられる。
- 悪い点: 実利用での「変える前」は取れない。実利用の値は、アクセスが増えるまで書けない。
- あとで困りうること: アクセスが増えないと、ADR 0025 決定 3 の比較（ラボの条件が実利用に対して甘すぎないか）がいつまでもできない。増える見込み（Phase 5 の SEO など）が立つまでは、ラボの関門だけで守る。

## オーナーに確認したいこと

なし（2026-10-04 に、案 C で進めること、件数の基準をオーナー以外も含めて端末ごとに 100 件程度とすることを確認した）。

## 追記

### 2026-10-04: `main` を測り、「変える前」のラボの値を書いた

- 本番の版（`main`。v1.2.1）と `develop`（9311fbe）を、いまの CI の条件で 3 台ずつ測った（数値は `docs/performance.md` の「変える前のラボの値」）。`main` は Performance 0.85〜0.87・LCP 約 1,815 ms・TBT 495〜568 ms・JS 247,958 B で、TBT と Performance の関門を超えた。`develop` は Performance 0.98・LCP 約 1,666 ms・TBT 145〜165 ms・JS 193,193 B。
- `main` には `scripts/` がないので、測る仕組み（`develop` の `scripts/lighthouse-ci.ts` と `lighthouserc.json`）を写してから測った。
