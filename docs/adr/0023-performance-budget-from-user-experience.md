# 0023. パフォーマンスの予算を、利用者の体験の目標から決める

- 状態: 採用
- オーナーの確認: 2026-09-29
- 日付: 2026-09-28
- 関連: M-2、ADR 0005 / 0009 / 0012 / 0015 / 0021 / 0022

## 背景

ADR 0012 決定 2 の予算のうち、JS の大きさの 2 つには、利用者の体験との結びつきがない。

- **JS の転送量 250,000 バイト（Lighthouse CI の関門）**: 決めたときの値（244,546 バイト）を丸めただけ。ADR 0012 の追記にも「増えていないことの見張り」と書いてある。超えると利用者が困る、という根拠はない。
- **`/` の First Load JS を「ベースラインから 20% 減」**: 20% の根拠が書かれていない。

ADR 0015（Next.js 16）の実装で、この 2 つが判断の役に立たないことが分かった（2026-09-28）。Next.js 16 に上げると JS が増え、250,000 バイトを超える。しかし、利用者の体験への影響を Lighthouse で測ると、JS の増え方と表示の遅れが比例しなかった。ローカルで 5 回ずつ回した中央値は次のとおり（モバイルの設定）。

| ビルド | JS の転送量 | LCP（ラボ） | TBT | Performance |
|---|---|---|---|---|
| Next 15 + webpack（いまの `develop`） | 211,634 B | 2,484 ms | 14 ms | 0.98 |
| Next 16 + webpack | 240,019 B（+28 kB） | 2,493 ms（+9） | 38 ms | 0.98 |
| Next 16 + Turbopack | 271,176 B（+60 kB） | 2,657 ms（+173） | 52 ms | 0.97 |

- 15 → 16 + webpack は +28 kB で LCP が +9 ms、16 + webpack → 16 + Turbopack は +31 kB で LCP が +164 ms。同じくらい JS が増えても、LCP への効き方が 18 倍違う。効くのは JS の量ではなく、どの JS が表示を待たせるか（チャンクの分け方）。
- バイト数を関門にすると、害のない変更を止め、害のある変更を通しうる。
- ラボの値は測るマシンで変わる。CI（GitHub Actions）の `develop` の LCP は約 1,810 ms（3 回のうち 2 回。1 回目は起動したばかりのサーバーが遅く 2,742 ms）で、ローカルより速い。Lighthouse は、測るマシンの速さを基準に遅い端末をまねるため。

いまの LCP の要素は、注意事項のモーダルの見出し（`<h2>`）。ページ全体が `"use client"` なので、JS が読み込まれて動くまで描かれない。そのため、いまは JS が LCP を直接待たせている。ADR 0005（ページの中身をサーバーで描く）と ADR 0009（注意事項のモーダルをやめる）で、この関係はなくなる見込み。

## 検討した選択肢

| 案 | 良い点 | 悪い点 |
|---|---|---|
| A. いまの値を丸めて、JS の転送量の関門を上げ直す（例: 280,000 バイト） | 変更が小さい | 根拠がないまま。次の変更ですぐ超え、また上げ直すことになる |
| B. 利用者の体験の目標から、JS の最大の大きさを逆算して関門にする | 根拠がある | 上の表のとおり、JS の量と LCP は比例しないので、逆算した値だけでは体験を守れない |
| **C. 利用者の体験の目標を、ラボの同じ指標でそのまま関門にする。JS の大きさは、逆算した「超えたら必ず失敗する上限」だけを関門にし、値は毎回 PR に出す** | 守りたいもの（表示の速さ・操作の反応）を直接守れる。JS の上限にも根拠がある | ラボの条件が実際の利用者に合っているかを、あとで確かめる必要がある |

## 決定

### 1. 最上位の目標は、実際の利用者の Core Web Vitals の「良い」の線にする

| 指標 | 目標（実際の利用者の p75） | 何を表すか |
|---|---|---|
| LCP | 2.5 秒以下 | ページの主な中身が表示されるまでの時間 |
| INP | 200ms 以下 | 操作してから画面が反応するまでの時間 |
| CLS | 0.1 以下 | 表示の途中で配置がずれる量 |

- どれも Google の Core Web Vitals の「良い」の線で、利用者の体験の調査から決められている。数字は ADR 0012 決定 2 と同じで、この ADR では「すべての予算の上位にある目標」と位置づける。
- 測るのは PostHog の `web_vital`（ADR 0021）。週に 1 回見て、超えていたら `docs/assessment.md` に足す（ADR 0012 決定 2 のまま）。

### 2. PR の時点では、Lighthouse のモバイルの設定を「基準の利用者」にする

- 実際の利用者の値は PR の時点では測れない。Lighthouse の既定のモバイルの設定（遅い 4G：1.6 Mbps・往復 150ms、4 倍遅い CPU）で、決定 1 と同じ指標を測って代わりにする。多くの利用者より遅い条件なので、ここで守れていれば実際の利用者でも守れる見込みが高い。
- 判定は CI（GitHub Actions）の値で行う（ラボの値はマシンで変わるため）。3 回の中央値。
- 実際の利用者の p75 が 1 週間分たまったら（ADR 0011 / 0012 の DoD）、同じ時期の CI の値と比べ、この条件が厳しすぎないか・甘すぎないかを見直して追記に書く。

### 3. CI の関門は、決定 1 の目標をそのまま決定 2 の条件に当てはめる

| 関門（Lighthouse CI、3 回の中央値） | 値 | 対応する目標 |
|---|---|---|
| `largest-contentful-paint` | 2,500 ms 以下 | LCP |
| `total-blocking-time` | 200 ms 以下 | INP（ラボでは測れないので、JS の処理で画面が固まる時間で代える。200ms は Lighthouse のモバイルの「良い」の線） |
| `cumulative-layout-shift` | 0.1 以下 | CLS（いまと同じ） |

- Performance（0.90 以上）・Accessibility・Best Practices・SEO の関門は変えない。ただし「Performance を CI の値の最小値に締める」（ADR 0012 の追記と DoD）はやめる。いまの値に合わせるだけの決め方で、決定 1 の目標とは結びつかないため。0.90 は Lighthouse が「良い」（緑）とする線なので、そのまま残す。

### 4. JS の大きさは、決定 2 の条件から逆算した上限だけを関門にする

- 決定 2 の条件で、LCP が JS を待つ限り、JS を送るのに使える時間は、LCP の予算から HTML と CSS が届くまでの時間（FCP。CI で約 760 ms）を引いた約 1,740 ms。
- 1.6 Mbps（1 秒に約 209,700 バイト）で 1,740 ms に送れるのは約 364,900 バイト。往復の時間や JS の処理の時間を 0 と見た値なので、これを超えると、ほかをどう工夫しても LCP の関門を満たせない。
- **`resource-summary:script:size` の関門を、250,000 バイトから 350,000 バイト（上の値を切り下げたもの）にする。** 「超えたら必ず失敗する上限」であり、ここまで増やしてよいという目安ではない。実際に守るのは決定 3 の LCP と TBT。
- JS の転送量は、関門とは別に、毎回 PR の CI の結果のコメントに出す（増えたことに気づけるように）。
- ADR 0005 / 0009 で LCP が JS を待たなくなったら、この逆算の前提が変わるので、上限を見直して追記に書く。

### 5. 「First Load JS をベースラインから 20% 減」の予算をやめる

- 根拠がなく、決定 3 / 4 で置き換える。ロードマップの Phase 2 の DoD「First Load JS がベースラインより減った」も、「決定 3 / 4 の CI の関門を満たしている」に置き換える。
- Next.js 16 のビルドは First Load JS を出力しなくなったので、JS の大きさは決定 4 の転送量で見る。

### 6. ADR 0012 決定 2 のうち、上の予算の部分をこの ADR で置き換える

`docs/performance.md` の予算の表を、この ADR に合わせて書き直す。ADR 0012 のほかの決定（計測の種類・重いものを遅れて読み込む方針・結果の残し方）は変えない。

## 結果

- 良い点: 予算がすべて「利用者の体験の目標」にさかのぼれる。JS の大きさを、根拠なく上げ直さなくてよくなる。ADR 0015（Next.js 16）を、利用者の体験で判断できる。
- 悪い点: ラボの LCP の関門は、いまの作り（LCP が JS を待つ）では余裕が小さい。CI では約 1.8 秒で 0.7 秒の余裕があるが、ローカルでは 2.48 秒で余裕がほとんどない。ADR 0005 / 0009 までは、LCP を悪くする変更が関門で止まりやすい。
- あとで困りうること: 決定 2 の条件が実際の利用者より厳しすぎると、利用者が困らない変更まで止める。実際の利用者の値がたまったら見直す（決定 2）。

## オーナーに確認したいこと

1. 決定 1 の目標（Core Web Vitals の「良い」の線を、実際の利用者の p75 で）でよいか。
2. PR の時点の基準の利用者を、Lighthouse の既定のモバイルの設定にすることでよいか。
3. JS の大きさを、逆算した「超えたら必ず失敗する上限」（350,000 バイト）だけ関門にし、実際には LCP と TBT で守ることでよいか。

**オーナーの回答（2026-09-29）**: すべて提案どおりでよい。

## 追記

### 2026-09-29: 実装

- `lighthouserc.json` に `largest-contentful-paint`（2,500 ms 以下）と `total-blocking-time`（200 ms 以下）の関門を足し、`resource-summary:script:size` を 350,000 バイトにした。どれも 3 回の中央値（`median-run`）。
- `scripts/lighthouse-summary.ts` を足した。`.lighthouseci/lhr-*.json` から LCP・TBT・CLS・JS の転送量・Performance を指標ごとに中央値で取り出し、`GITHUB_OUTPUT` に書く。CI の `lighthouse` ジョブで関門を超えたときにも走らせ、`report` ジョブの PR のコメントに表で出す。CI の Node 24 は TypeScript の型を外して実行できるので、`.ts` のまま `node` で実行している。
  - Lighthouse CI の `median-run` は、Performance の点数などで「真ん中の 1 回」を選んでその回の値で判定する。コメントの値は指標ごとの中央値なので、関門の判定に使われた値と少し違うことがある。
- `__tests__/scripts/lighthouse-budget.test.ts` で、`lighthouserc.json` の関門の値と、中央値の取り方（起動直後の遅い 1 回目に引きずられないこと）を確かめる。
- `develop`（ADR 0022 まで）の CI の値を、このスクリプトで取り出すと、LCP 1,814 ms・TBT 65 ms・CLS 0・JS の転送量 211,637 B・Performance 0.99。どれも関門の内。
