# 0026. ブラウザの Sentry を、ページの読み込みのあとに読み込む

- 状態: 採用
- オーナーの確認: 2026-10-03
- 日付: 2026-10-03
- 関連: docs/assessment.md の M-4 / ADR 0007 / 0009 / 0023 / 0024 / 0025

## 背景

ADR 0025 で、CI の Lighthouse の基準の端末を、Lighthouse が想定している端末（benchmarkIndex 440。CI のマシンの単位）に固定した。この条件では、いまの `develop` の TBT が 223〜245 ms になり、関門（200 ms。ADR 0023 決定 3）を超える。関門も基準も緩めず、先に TBT を減らすことにした（ADR 0025 のオーナーの回答）。

何が TBT を占めているかを、部品を外したビルドどうしの差で調べた（2026-10-03）。

- 手元（Apple M4）で、CPU の倍率を 14 にして測った。手元のマシンは CI より速いので、倍率 14 が CI の基準の端末に近い TBT になる（ADR 0025 の背景の、手元と CI の曲線から）。
- 変種ごとに別のディレクトリでビルドしてサーバーを並べ、1 巡ずつ交互に測った（温める 2 回を捨て、7 回の中央値）。手元のマシンの速さは日や時刻で変わる（benchmarkIndex 3,300〜3,700）ので、比べるのは同じ組の中だけにする。
- 「Sentry 有効」は、本番と同じく DSN がある状態。送り先のない DSN（127.0.0.1 の 9 番）を使い、どこにも送っていない。CI と手元の普段のビルドは DSN がなく、Sentry は無効（`enabled: false`。ADR 0007 決定 5）。

**組 1: 何が占めているか**

| ビルド | TBT（最小〜最大） | LCP | `/` の JS の転送量 |
|---|---|---|---|
| いまの `develop`（Sentry 無効。CI と同じ） | 306 ms（286〜326） | 2,433 ms | 171,862 B |
| いまの `develop`（Sentry 有効。本番と同じ） | 346 ms（325〜476） | 2,465 ms | 171,895 B |
| 注意事項のモーダルを自動で開かない | 257 ms（248〜306） | 2,413 ms | 171,856 B |
| Sentry の初期化（`instrumentation-client.ts`）を外す | 160 ms（156〜178） | 2,060 ms | 148,660 B |
| ブラウザ側から Sentry をすべて外す | 155 ms（144〜282） | 2,060 ms | 144,620 B |
| 上に加えて、結合の画面・モーダル・Web Vitals も外す（Next.js と React だけ） | 118 ms（108〜184） | 2,047 ms | 135,124 B |
| `import("@sentry/nextjs")` で、load のあとに読み込む | 237 ms（225〜284） | 2,050 ms | 307,362 B |

**組 2: 直し方の比較**

| ビルド | TBT（最小〜最大） | LCP | `/` の JS の転送量 |
|---|---|---|---|
| いまの `develop`（Sentry 無効） | 289 ms（275〜318） | 2,411 ms | 171,862 B |
| いまの `develop`（Sentry 有効） | 350 ms（321〜357） | 2,470 ms | 171,895 B |
| 既定の統合機能をやめ、エラーの監視に要るものだけにする（Sentry 有効） | 326 ms（292〜362） | 2,449 ms | 173,087 B |
| 必要な関数だけを書き出すモジュールを経由して、load のあとに読み込む（Sentry 無効） | 138 ms（123〜168） | 2,064 ms | 174,073 B |
| 同上（Sentry 有効） | 144 ms（124〜178） | 2,073 ms | 174,112 B |
| 同上（Sentry 有効）に加えて、モーダルを自動で開かない | 103 ms（95〜143） | 2,061 ms | 174,104 B |

分かったことは 5 つある。

1. **TBT の半分ほどは、Sentry の初期化とその読み込みが占めている。** 初期化を外すと、TBT は 306 → 160 ms、LCP は 2,433 → 2,060 ms になった。Sentry が無効（DSN がない）でも、SDK の読み込みと初期化の処理は走る。初期化を外すと `/` の JS も約 23 kB 減る（SDK の大半が、初期化から読み込まれているため）。
2. **本番（Sentry 有効）は CI より重い。** 同じビルドで、Sentry を有効にすると TBT が 40〜61 ms 増えた。CI の関門は Sentry が無効の状態で測っているので、本番の利用者の体験より甘く出ている。
3. **load のあとに読み込めば、Sentry を残したまま、外したときと同じくらいまで減る。** 必要な関数（`init` / `addBreadcrumb` / `captureException`）だけを書き出すモジュールを経由すると、Sentry 有効で 350 → 144 ms、LCP は 2,470 → 2,073 ms になった。ただし `import("@sentry/nextjs")` と直接書くと、使わない機能まで含めて SDK の全部が読み込まれ（JS が 307 kB）、かえって悪くなる。
4. **統合機能を絞るだけでは足りない**（350 → 326 ms）。
5. **注意事項のモーダルを自動で開くのに、約 40〜50 ms かかる**（組 1 で 306 → 257 ms、組 2 で 144 → 103 ms）。読み込みの直後に、モーダルを開くための 2 回目の描画が走るため。

CI の基準の端末で、いまの `develop` は 223〜245 ms だった。組 2 の割合（289 → 138 ms。約 52% 減）が CI でも同じなら、load のあとに読み込む案で 110〜120 ms ほどになり、関門の内に入る見込み。これは手元の割合からの推定で、CI では測っていない。

## 検討した選択肢

| 案 | 良い点 | 悪い点 |
|---|---|---|
| A. ブラウザ側の Sentry をやめる | TBT と JS が最も減る | ブラウザで起きた想定外の例外が見えなくなる（ADR 0007 の目的に反する） |
| B. 既定の統合機能をやめ、要るものだけにする | 変更が小さい | 減る量が小さく（約 24 ms）、関門の内に入らない |
| C. 注意事項のモーダルを自動で開かない | 約 40〜50 ms 減る | 減る量が足りない。利用者に見える流れが変わり、ADR 0009（画面の流れ）の範囲。結合をブラウザの中に移すと（ADR 0002）、モーダルの役目そのものが変わる |
| **D. Sentry を、必要な関数だけのモジュールを経由して、load のあとに読み込む** | Sentry を残したまま、外したときと同じくらい減る。LCP も 400 ms ほど減る。本番（Sentry 有効）ほど効く | load の前に起きたエラーは、Sentry が自動では拾わない（決定 2 で補う）。読み込みの仕組みのコードが増える |

## 決定

1. **ブラウザの Sentry を、ページの `load` のあとに読み込んで初期化する。** SDK は `lib/sentry/client.ts`（`init` / `addBreadcrumb` / `captureException` など、使う関数だけを書き出す）を経由して、動的な import で読み込む。読み込みと初期化は 1 回だけ行い、その Promise をほかの呼び出しと共有する。サーバーと Edge の Sentry は変えない。
2. **load の前に起きたエラーを取りこぼさない。** `instrumentation-client.ts` で、最初に `error` と `unhandledrejection` を受けるだけの小さな受け口を置き、Sentry の初期化までに起きたものをためておく（上限は 10 件）。初期化したら `captureException` で送り、受け口を外す（そのあとは Sentry の自動の受け口が拾う）。送る内容は、ほかのエラーと同じく `beforeSend` で消す（ADR 0007 決定 1）。
3. **パンくずと `captureException` は、初期化のあとにだけ渡す。** 結合の操作のパンくず（ADR 0024）と、`global-error` の `captureException` は、決定 1 の Promise を待ってから呼ぶ。初期化の前に操作があったときは、そこで読み込みと初期化を始める。こうすると、`beforeBreadcrumb` での消し込み（ADR 0007 決定 1）が必ず通る。
4. **ブラウザ側のコードで `@sentry/nextjs` を直接 import しない。** `lib/sentry/client.ts` と、型だけの import と、サーバー・Edge の設定は除く。うっかり直接 import すると、SDK が最初の読み込みに戻るので、lint（Biome）で止める。
5. **注意事項のモーダルは、この ADR では変えない。** 見せ方の見直しは ADR 0009 で行う。

## 結果

- 良い点: 基準の端末で TBT が関門の内に入る見込みで、ADR 0025 の補正を入れられるようになる。LCP も減る。本番（Sentry 有効）ほど効くので、実際の利用者の体験が良くなる。
- 悪い点: Sentry の自動の受け口が動き始めるのが load のあとになる。それまでのエラーは決定 2 の受け口で拾うが、load の前に利用者がページを離れると、ためたエラーは送られない。読み込みの仕組みのコードが増える。
- あとで困りうること: CI での減り方が手元の推定より小さく、関門の内に入らないかもしれない。そのときは、結果を追記に書き、次に効く部品（モーダルの自動表示。ADR 0009）の扱いを相談する。

## 追記

### 2026-10-03: 実装した

- `lib/sentry/client.ts` は `init` / `addBreadcrumb` / `captureException` だけを書き出す。`lib/sentry/lazy.ts` の `createLazySentry` が、読み込みと初期化（1 回だけ）、初期化までのエラーの受け口（決定 2）、初期化を待ってから渡すパンくずと `captureException`（決定 3）を持つ。読み込めなかったとき（チャンクの取得の失敗など）は、送る先がないので何もしない。`lib/sentry/browser.ts` がその 1 つだけの入り口で、`instrumentation-client.ts` は受け口を置いて、`runAfterLoad`（load のあとの次のタスク）で初期化を始めるだけにした。
- 決定 4 は、Biome の `style/noRestrictedImports` を `overrides` で `app/**`・`components/**`・`hooks/**`・`lib/**`・`instrumentation-client.ts` に有効にし、`lib/sentry/client.ts` と `lib/sentry/options.ts`（型だけの import）を除いた。Biome には型だけの import を許す設定がないため。ユニットテストでは、一時ディレクトリに `biome.json` と検査用のファイルを置いて lint を走らせる（標準入力で渡すモードでは、lint の診断が出ないため）。
- E2E（`e2e/sentry.spec.ts`）で、load の時点では SDK（グローバルの `__SENTRY__`）がなく、そのあとに読み込まれることを確かめる。このテストは、いまの `develop` では失敗する（load の時点で SDK がある）。
- `/` の First Load JS は 165 kB → 139 kB（共有のチャンクは 134 kB → 107 kB）。SDK は、load のあとに読み込むチャンク（圧縮前 80 kB）に移った。Pages Router（Next.js の 404 などに使う `_app`）にも同じ入り口とチャンクができるが、`/` では読み込まれない。

### 2026-10-03: CI では、手元の推定ほどは減らなかった

ADR 0025 の補正の条件（温める 2 回の benchmarkIndex の大きいほう ÷ 440 を倍率にする）で、同じマシンに `develop` とこの実装のサーバーを並べ、交互に 7 回ずつ測った（一時的なワークフロー。マージせずに消した）。

| マシン（benchmarkIndex の大きいほう・倍率） | `develop` の TBT（最小〜最大） | この実装の TBT（最小〜最大） | LCP（両方） |
|---|---|---|---|
| AMD EPYC 7763（2,460・5.59） | 246 ms（233〜265） | 212 ms（174〜225） | 1,663〜1,665 ms |
| AMD EPYC 7763（2,488・5.65） | 228 ms（222〜252） | 184 ms（175〜196） | 1,663〜1,665 ms |
| AMD EPYC 7763（2,458・5.59） | 236 ms（230〜259） | 199 ms（185〜217） | 1,663〜1,665 ms |

- TBT は 34〜44 ms（15〜19%）減ったが、関門（200 ms）の前後にとどまり、DoD の 5 つ目は満たせていない。手元の倍率 14 での「約 52% 減」は CI に当てはまらなかった。手元の割合から CI を推定した背景の最後の段落は、外れた。
- LCP は、CI では JS を待たない山（ADR 0025 の背景）にいるので変わらない。

### 2026-10-03: CI で測った内訳

上と同じ条件で、部品を外したビルドを 6 つ並べ、交互に 7 回ずつ測った（一時的なワークフロー。マージせずに消した）。「Sentry 有効」は、送り先のない DSN（127.0.0.1 の 9 番）でビルドしたもの。

| ビルド | EPYC 7763（倍率 5.63） | EPYC 9V74（倍率 7.03） | EPYC 7763（倍率 5.63） |
|---|---|---|---|
| `develop` | 232 ms | 213 ms | 237 ms |
| この実装 | 200 ms | 173 ms | 199 ms |
| この実装 ＋ 注意事項のモーダルを自動で開かない | 147 ms | 128 ms | 149 ms |
| Next.js と React だけ（Sentry・モーダル・結合の画面・Web Vitals を外す） | 134 ms | 120 ms | 138 ms |

（TBT の中央値。LCP はどれも 1,659〜1,673 ms）

- **CI の条件（Sentry 無効）では、残りの大半は注意事項のモーダルの自動表示**（45〜53 ms）。モーダルを自動で開かないと、Next.js と React だけのときとの差は 8〜13 ms になる。
- **本番の条件（Sentry 有効）では、この実装でも 197〜239 ms ある。** load のあとに回した Sentry の初期化も、Lighthouse の TBT が数える範囲（FCP から操作できるようになるまで）に入るため。`develop`（Sentry 有効）との差は 25〜52 ms。
- CI の関門は Sentry が無効の状態で測っているので、本番より 23〜43 ms 甘い（`develop` どうし、この実装どうしで比べた差）。
