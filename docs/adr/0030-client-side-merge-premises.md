# 0030. ブラウザでの結合（ADR 0002）を実装する前に、変わった前提を決め直す

- 状態: 採用
- オーナーの確認: 2026-10-04
- 日付: 2026-10-04
- 関連: docs/assessment.md の B-2 / B-4 / P-1 / P-4 / ADR 0002 / 0009 / 0011 / 0023 / 0027 / 0029

## 背景

ADR 0002（結合をブラウザの Web Worker で行い、PDF をサーバーへ送らない）は 2026-09-27 に採用した。Phase 3 でこれを実装する前に読み直すと、そのあとに次のことが変わっていた。

1. **JS の関門ができた。** ADR 0023 / 0025 / 0028 で、`/` の最初の読み込みの TBT・JS の転送量に関門を設けた。結合に使う `pdf-lib` は、圧縮して gzip にすると約 206 KB（`pdf-lib.min.js`）あり、いまの `/` の JS 全体（約 193 KB）より大きい。
2. **Next.js 16（Turbopack）になった。** ADR 0002 を書いたときは webpack の前提だった。
3. **実利用のベースラインがない。** 本番のアクセスがほとんどなく、ADR 0029 で実利用の値は件数がたまってから書くことにした。Phase 3 の DoD の「`merge_failed` の率がベースラインより悪化していない」は判定できない。ADR 0002 決定 5 の「警告のしきい値は Phase 1 の計測で見直す」も、見直す材料がない。
4. **注意事項の出し方を変えた。** ADR 0027 で、モーダルをやめてドロップ領域の下に断りを出した。ADR 0002 を本番に出すときに、文言を「ファイルはこの端末の中だけで処理され、外部へ送信されません」に替える約束になっている。
5. **ファイルごとの印を出す画面（ADR 0009）は Phase 4。** ADR 0002 決定 4 は「読めないファイルは一覧に印を付け、ほかのファイルの結合は止めない」としているが、印の見せ方は ADR 0009 に任せていて、まだ作っていない。

### Worker を試した（2026-10-04）

作業用のコピーで、`new Worker(new URL("../workers/probe.worker.ts", import.meta.url), { type: "module" })` で `pdf-lib` を読み込む Worker を作り、Next.js 16.3.5（Turbopack）でビルドしてヘッドレスの Chromium で動かした。

- Turbopack は Worker 用の起動のコード（`turbopack-worker-*.js`）を作り、その中から `pdf-lib` を含むチャンク（圧縮前 424 KB・gzip 175 KB）を読み込んだ。Worker は結合した PDF（空のもの、583 バイト）をページに返した。
- `pdf-lib` のチャンクは、Worker を作ったあとにだけ読み込まれた。ページの最初の HTML が読み込む JS には入っていなかった。
- Worker のファイルは `.ts` のまま `static/media` にもコピーされたが、使われなかった。
- Worker の中の `self.postMessage` は、プロジェクトの型（DOM）ではページ向けの型になるので、型を合わせる必要がある。

## 検討した選択肢

**読めない PDF の扱い（Phase 3 の間）**

| 案 | 良い点 | 悪い点 |
|---|---|---|
| A. 追加したときに 1 つずつ読んで確かめ、読めないものは一覧に入れない | 結合のときに失敗しない | 同じファイルを 2 回読む（追加のときと結合のとき）。大きいファイルでは追加が遅くなる |
| **B. 結合のときに 1 つずつ読み、読めないものは飛ばして残りで結合する。飛ばしたファイルの名前と理由を画面に出す** | 1 回しか読まない。ADR 0002 決定 4 の「ほかのファイルの結合は止めない」を満たす | 一覧の行の印（ADR 0009）は Phase 4 まで出ない。結合のあとまで、読めないことが分からない |
| C. ADR 0009 の一覧の印を Phase 3 で先に作る | ADR 0002 の形がそのまま入る | Phase 4 の画面づくり（Claude Design で作る。ADR 0008）を先取りすることになり、範囲が広がる |

**リリースの分け方**

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **ア. ADR 0002 だけを先に出す（ADR 0003 / 0017 は別のリリース）** | 変更が小さく、問題が出たときに原因を切り分けやすい。API を残す（ADR 0002 決定 6）ことでの戻しやすさも確かめやすい | リリースの回数が増える |
| イ. ADR 0002 / 0003 / 0017 をまとめて出す | リリースは少ない | 問題が出たときに、どれが原因か分かりにくい |

## 決定

1. **`pdf-lib` は Worker の中でだけ読み込み、最初の読み込みに入れない。** `new Worker(new URL(..., import.meta.url), { type: "module" })` で作り、Worker は結合を始めたときに作る。E2E で「結合する前に、Worker の起動のコード（`turbopack-worker-*.js`）を読み込んでいない」ことを確かめる（CI の Lighthouse は最初の読み込みしか見ないため）。
2. **読めない PDF は、結合のときに飛ばして残りで結合する（案 B）。** 1 つずつ読み、パスワード付き（`EncryptedPDFError`）と壊れたもの（読み込みの失敗）を飛ばす。飛ばしたファイルの名前と理由（「パスワード付きのため」「読み込めないため」）を、結合の操作の近くに文言で出す。ファイル名は画面に出すだけで、アナリティクス・Sentry には送らない（ADR 0007 / 0011）。すべて読めなかったときは、結合の失敗として出す。一覧の行の印は ADR 0009（Phase 4）で作る。
3. **アナリティクスのイベントを、`docs/analytics.md` の予定どおりに変える。** 飛ばしたファイルは `files_rejected` の `reason` に `encrypted` / `corrupt` を足して数える（数は区間）。`merge_failed` の `reason` は `worker_error` / `out_of_memory` / `no_valid_files` / `unknown` にする。`payload_too_large` / `server_error` / `network_error` は、ブラウザで結合するようになった時点で送らなくなる。
4. **警告のしきい値（ADR 0002 決定 5）は、初期値（合計 300MB / 100 ファイル）で始める。** 見直すのは、ADR 0029 の件数の基準を満たしたときか、失敗の報告が来たとき。リリースの前に、`perf/merge-timing.spec.ts` をブラウザでの結合に合わせて直し、手元で 20MB・100MB の結合の時間を測って `docs/performance.md` に書く。
5. **Phase 3 の DoD の「`merge_failed` の率がベースラインより悪化していない」を置き換える。** 「リリース後 1 週間、Sentry に結合の想定外のエラー（`worker_error` / `unknown` にあたるもの）が新たに出ていない。ADR 0029 の件数の基準を満たしたら、`merge_failed` の率を比べる」にする。
6. **Phase 3 の最初のリリースは、ADR 0002 だけにする（案ア）。** ADR 0027 の断りの文言も、このリリースで替える。API（`app/api/merge-pdf/`）は、その次のリリースで消す（ADR 0002 決定 6）。ADR 0003（プレビュー）と ADR 0017（ヘッダ・CSP）は、別のリリースで出す。

ADR 0002 決定 5 の「値は Phase 1 の計測で見直す」は、この ADR の決定 4 で置き換える。ADR 0002 のほかの決定は変えない。`pdf-lib` を続けるか、メンテナンスされているフォーク（`@cantoo/pdf-lib`。最新は 2.11.1、2026-09-15 公開）に替えるかは、ADR 0002 決定 3 のとおり、実装のときに互換性と大きさを比べて追記に書く。

## 結果

- 良い点: 最初の読み込みの JS を増やさずに、ブラウザでの結合に移れる。Phase 4 の画面づくりを先取りせずに、ADR 0002 の約束（ほかのファイルの結合を止めない）を守れる。判定できない DoD を、判定できるものに置き換える。
- 悪い点: Phase 3 の間は、読めないファイルが結合のあとまで分からない。リリースの回数が増える。
- あとで困りうること: 結合のときに初めて `pdf-lib`（gzip で約 175 KB）を読み込むので、遅い回線では最初の結合が少し遅れる。結合のボタンにマウスを乗せたときなどに先に読み込むかは、実装のときに測って決める。

## 追記

### 2026-10-07: 実装で決めた詳細

- **決定 1**: Worker の起動のコード（`turbopack-worker-*.js`）と `pdf-lib` のチャンク（圧縮前 424 KB・gzip 175 KB）は、結合を始めたときにだけ読み込まれた。ページの最初の HTML が読み込む JS には入っていない（ビルドのチャンクの中身と、E2E で確かめた）。E2E は、ファイルを追加して通信が落ち着くまでに起動のコードを読まないこと、結合したあとには読んだこと（見落としていないこと）の両方を見る。Firefox・WebKit でも Worker のリクエストを `context.on("request")` で拾えた。
- **決定 2**: 飛ばしたファイルは、ステップ 3 の操作のボタンの下に「次のファイルは結合に含めていません。」と、名前と理由の箇条書きで出す（`components/merge/skipped-files.tsx`）。結合が終わったときに読み上げられるよう `aria-live="polite"` の入れ物を常に置く（`role="status"` の `div` は Biome の a11y のルールが `<output>` を求め、`<output>` には箇条書きを入れられないため）。一覧を変えると消す。すべて読めなかったときは「結合できる PDF がありませんでした」をエラーとして出し、飛ばしたファイルも並べる。
- **決定 3**: `files_rejected` の `encrypted` / `corrupt` は、結合のたびに理由ごとに 1 件、飛ばした数の区間で送る。`merge_failed` の `no_valid_files` の前に送る。
- **「あとで困りうること」の先読み**: 結合のボタンにマウスを乗せたときに先に読み込むことは、まだしていない。手元では、各組の 1 回目（読み込みを含む）と 2 回目以降の差は数十〜百 ms 程度（`docs/performance.md`）。遅い回線での差を測ってから決める。
