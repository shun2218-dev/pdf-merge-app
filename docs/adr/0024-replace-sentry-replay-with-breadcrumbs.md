# 0024. Sentry の Session Replay をやめ、操作のパンくずを自分で残す

- 状態: 採用
- オーナーの確認: 2026-10-01
- 日付: 2026-10-01
- 関連: ADR 0005 / 0007 / 0011 / 0015 / 0022 / 0023

## 背景

ADR 0007 決定 2 で、Sentry の Session Replay を「エラーが起きたときだけ・画面の文字と画像をすべて隠して」使うことにした。エラーの前に利用者が何をしたかを見るためである。ただ、何を見たいのか、ほかの手段では足りないのかは確かめていなかった。

ADR 0015（Next.js 16）の調査で、Replay の重さが分かった（2026-10-01）。

- **JS**: Replay のコード（rrweb）は、`/` が最初に読み込む JS のうち gzip で約 37 kB（Next.js 15 の webpack のビルドのチャンク）。いまの JS の転送量（約 212 kB）の 2 割近い。Next.js 16 + Turbopack のビルドで外すと、279.8 kB → 240.6 kB（−39 kB）だった。
- **TBT**: 手元で、中位のスマートフォンに相当する条件で測ると、外したときに TBT が 28〜38 ms 減った（測定の揺れが大きいので目安。ADR 0015 の追記）。
- **動き方**: 「エラーのときだけ送る」設定でも、Replay はすべての利用者のページで画面の変化を記録し続け、エラーが起きたときに直前の分だけを送る（バッファの方式）。エラーが起きない大多数の利用者でも、記録の処理は動いている。

一方で、Replay がなくても残るものを確かめた。`develop` を偽の Sentry の受け口に向けてビルドし、注意事項のモーダルを閉じ → PDF を 1 つ足し → 通信が失敗する状態で「プレビュー」を押した。

- エラーのイベントは届き、ファイル名は含まれていなかった（ADR 0007 決定 1 のとおり）。
- パンくず（breadcrumb）には、ページの表示と 4 回のクリック（`ui.click`）が残った。ただし、クリックの記録は Tailwind のクラス名の羅列（`button.inline-flex.items-center…flex-1.bg-transparent` など）で、「プレビュー」と「ダウンロード」のどちらを押したかは、クラスのわずかな違いから推し量るしかない。
- ファイルを足した・消した・並び替えたなど、クリックでない操作はパンくずに残らない。

Replay だけが担っているのは「画面がどう見えていたか」だが、文字も画像も隠しているので、分かるのは配置とクリックの位置くらいである。このアプリは 1 ページで、操作も「足す・並び替える・消す・プレビュー・ダウンロード」しかない。操作の順番が正確に分かれば、エラーの前の状況はほぼ再現できる。

## 検討した選択肢

| 案 | 良い点 | 悪い点 |
|---|---|---|
| A. いまのまま | 変更がない | JS 約 37 kB と TBT を、エラーの起きない利用者を含む全員が負担する。分かるのは隠した画面の配置だけ |
| B. Replay をページの読み込みのあとに遅れて読み込む | 最初の JS から外れる | 読み込んだあとは同じく記録し続ける。読み込みの前に起きたエラーは記録されない。作りが複雑になる |
| **C. Replay をやめ、結合の操作をパンくずとして自分で残す** | JS と TBT が減る。操作の順番が、クラス名の羅列ではなく意味のある名前で残る。送るものが減る（画面の構造を送らない） | 画面の見た目は見られなくなる |

案 C のために、Sentry の `reactComponentAnnotation`（クリックの記録にコンポーネント名を付ける）も調べたが、webpack のビルドにしか効かない（Next.js 16 の Turbopack では使えない。ADR 0015）ので選ばない。

## 決定

1. **Sentry の Session Replay をやめる。** `instrumentation-client.ts` から `replayIntegration` と `replaysSessionSampleRate` / `replaysOnErrorSampleRate` を外す。ADR 0007 決定 2 をこの ADR で置き換える。
2. **結合の操作を、Sentry のパンくずとして自分で残す。** `use-merge-workflow`（ADR 0005）の操作ごとに `Sentry.addBreadcrumb` を呼ぶ。カテゴリは `merge`、内容はアナリティクスと同じ区間（バケット）の値だけにする（ADR 0011 決定 3）。ファイル名・ファイルの中身は入れない。
   - 例: `files_added`（`count_bucket`・`size_bucket`）、`files_rejected`、`file_removed`、`files_reordered`、`merge_started`、`merge_succeeded`、`merge_failed`（`reason`）、`preview_opened`、`download_clicked`
   - アナリティクスのイベントを送る関数（`track`）と同じ場所で残す。名前と値をそろえ、PostHog と Sentry を突き合わせやすくする。
3. **Sentry が自動で残すパンくず（クリック・通信・画面遷移・コンソール）は、そのまま使う。** ファイル名を `[file]` に置き換える処理（ADR 0007 決定 1）も変えない。

## 結果

- 良い点: `/` が最初に読み込む JS が約 37 kB 減り、読み込みのときの処理（TBT）も減る見込み。エラーの前の操作が、意味のある名前で順番どおりに残る。画面の構造を Sentry に送らなくなる。
- 悪い点: エラーのときの画面の見た目（隠した配置）は見られなくなる。
- あとで困りうること: 画面の見た目に関わる不具合（表示の崩れなど）は、パンくずだけでは分かりにくい。そうした不具合が続いたら、Replay を遅れて読み込む案（B）を改めて検討する。

## 追記

### 2026-10-01: 実装と確認

- `instrumentation-client.ts` から `replayIntegration` と Replay のサンプリングの設定を外した。`__tests__/lib/sentry.test.ts` で、ファイルに Replay の設定がないことを確かめる。
- `hooks/use-merge-workflow.ts` に `record(name, properties)` を置き、アナリティクスの `track` と `Sentry.addBreadcrumb`（カテゴリ `merge`、`message` にイベント名、`data` に値。`merge_failed` だけ `warning`）を同じ値で呼ぶ。フックの中の `track` の呼び出しをすべて `record` にした。フックのテストで、パンくずの名前と値がアナリティクスと一致し、ファイル名が入らないことを確かめる。
- **大きさ**: `/` の First Load JS は 206 kB → 165 kB（−41 kB）、共通のチャンクは 175 kB → 134 kB。Replay のコード（rrweb）はビルドした JS から消えた。`rrweb` という文字は PostHog が遅れて読み込むチャンクに残るが、PostHog の互換のための名前で、最初には読み込まれない。
- **偽の受け口での確認**: `develop` と同じ手順（PDF を 2 つ足す → PDF 以外をドロップ → 1 つ削除 → 通信が失敗する状態で「プレビュー」）で、エラーのイベントのパンくずが `files_added` → `files_rejected` → 削除のクリック → `file_removed` → 「プレビュー」のクリック → `merge_started` → `merge_failed`（`network_error`）の順に入った。ファイル名は含まれず、Replay のデータ（`replay_event` / `replay_recording`）は送られなかった。
- #85 の CI の LCP は 2,273 ms（関門の内）で、前の PR の約 1,820 ms より大きく出た。同じ速さのマシン（benchmarkIndex 約 2,350）の 2 回で 1,668 ms と 2,273 ms に分かれており、LCP の要素（JS が動いてから出る注意事項のモーダルの見出し）のタイミングによる揺れと判断した。CI の回数と基準の端末は、次の ADR（基準の端末を決める）で扱う。
