# 0013. 国際化（next-intl、日本語と英語）

- 状態: 提案
- オーナーの確認: 未
- 日付: 2026-09-27
- 関連: I-1、ADR 0008 / 0009 / 0010 / 0014 / 0015 / 0016

## 背景

- 文言はすべて日本語で、コンポーネントに直書きされている（I-1）。
- PDF の結合は言語に依存しない需要で、英語で探す人のほうがはるかに多い。ADR 0002 で「ファイルを送らない」ことが強みになれば、英語圏にも出す価値がある。
- `formatFileSize` が `1.5 MB` のような表記を自前で組み立てている。言語によって数字や単位の書き方は変わる。
- `<html lang="ja">` が固定。

## 検討した選択肢

| 案 | 良い点 | 悪い点 |
|---|---|---|
| **A. `next-intl`** | App Router とサーバーコンポーネントに対応。ルーティング・メタデータ・`Intl` の書式・型付きのキーが揃う | 依存が 1 つ増える |
| B. `react-i18next` | 定番 | サーバーコンポーネントとの組み合わせに手間がかかる |
| C. 自前の辞書（`dictionaries/ja.json` を読むだけ） | 依存ゼロ | 複数形・書式・ロケールの判定・リダイレクトを自前で書く |

## 決定

**A を採る。**

1. **対応する言語は日本語（既定）と英語。** ほかの言語は、アナリティクス（ADR 0011）で国の分布を見てから別の ADR で決める。
2. **URL にロケールを入れる。** 日本語は接頭辞なし（`/`）、英語は `/en`（next-intl の `localePrefix: "as-needed"`）。検索エンジンに言語ごとの URL を渡すため（ADR 0016 の hreflang）。
   - 初回の訪問では `Accept-Language` を見て、英語の人を `/en` へ案内する。選んだ言語は Cookie（`NEXT_LOCALE`）に残し、以後はそれを優先する。
   - ロケールの判定は Next.js 16 の `proxy.ts`（ADR 0015）で行う。
3. **文言は `messages/ja.json` と `messages/en.json` に置く。** キーは画面と部品で区切る（例: `merge.dropZone.title`）。
   - next-intl の型の拡張で、存在しないキーを使うとコンパイルエラーにする。
   - **日本語と英語でキーの集合が一致すること**をテストで検査し、CI の `i18n` ジョブにする（ADR 0006）。
   - コンポーネント・メタデータ・`aria-label`・読み上げの文言（ADR 0010）・トースト・エラーのすべてを辞書から引く。日本語の直書きを lint で検出する（biome のカスタムルールが使えなければ、日本語の文字を含む JSX のテキストを `grep` で検査するスクリプトを CI に置く）。
4. **数・大きさ・日付は `Intl` で書式化する。** ファイルの大きさは `Intl.NumberFormat` の `style: "unit"`（`kilobyte` / `megabyte`）。自前の `formatFileSize` を消す。
5. **`<html lang>` をロケールに合わせる。** メタデータ（タイトル・説明・OGP）もロケールごとにする（ADR 0016）。
6. **ヘッダーに言語の切り替えを置く。** 切り替えても、追加したファイルの一覧は保つ（同じページの中でロケールだけを変える。ページを読み直さない）。
7. **英語の文言は、最初は Claude で翻訳し、オーナーが確認する。** 用語集（PDF / merge / reorder などの訳語）を `docs/i18n.md` に置き、訳を揃える。

## 結果

- 良い点: 英語圏の検索から利用者が来られる。文言が 1 箇所にまとまり、言い回しの統一もしやすい。
- 悪い点: 文言を変えるたびに 2 言語を更新する手間がかかる。`app/page.tsx` などが `app/[locale]/` の下に移るので、パスが変わる。
