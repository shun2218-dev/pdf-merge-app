# 0025. CI の Lighthouse の基準の端末を固定し、温める回を捨てる

- 状態: 提案
- オーナーの確認: 未（2026-10-02 に、決定 1・2・4・5 の進め方と、決定 3 を書き直す方向に了承をもらった。CI で測った結果を入れて書き直したこの本文と、「オーナーに確認したいこと」の返事を待っている）
- 日付: 2026-10-02
- 関連: ADR 0006 / 0012 / 0015 / 0021 / 0023

## 背景

ADR 0023 決定 2 は、PR の時点の「基準の利用者」を Lighthouse の既定のモバイルの設定（遅い 4G・4 倍遅い CPU）にし、判定を CI の値で行うとした。実装してみると、CI の値が利用者の体験と関係のない理由で大きく揺れ、関門の合否がそれで決まりうることが分かった。

CI に残っている Lighthouse の結果から、アプリのコードが同じで文書だけが違う実行を 2 組（各 5 回の実行 × 3 回の測定）集めて調べた（2026-10-02）。

| 組 | コード | 1 回目 | 2・3 回目のマシンの速さ（benchmarkIndex） | 2・3 回目の LCP | 2・3 回目の TBT |
|---|---|---|---|---|---|
| A | ADR 0024 のあと | 5 回中 3 回で外れ値 | 2,342〜2,472 | 1,513〜2,273 ms（中央値 1,666） | 125〜178 ms |
| B | ADR 0005 のあと | 5 回中 5 回で外れ値 | 2,338〜2,487 | 1,815〜1,821 ms | 148〜193 ms |

CI に残っている結果から分かったことは 3 つある。

1. **1 回目だけが大きく外れる。** 10 回の実行のうち 8 回で、1 回目の LCP が 2.5〜3.5 秒、TBT が 600〜2,700 ms になった。そのとき Lighthouse が測ったマシンの速さも 720〜1,970 に落ちている。起動したばかりのサーバーと Chrome が CPU を取り合っているためと考えられる。3 回の中央値で判定しているので多くは救われるが、残りの 2 回のどちらかもぶれると外れ値が選ばれる（#85 の LCP 2,273 ms）。
2. **2・3 回目は安定している。** B 組の LCP は 10 回とも 1,815〜1,821 ms だった。
3. **日によってマシンが変わる。** 2026-09-28 の実行ではマシンの速さが 4,150〜4,490 で、いまの倍近かった。そのころの `develop` の TBT は 58〜65 ms、いまは 150 ms 前後。Lighthouse の「4 倍遅い CPU」は測るマシンを基準にした倍率なので、GitHub のマシンの世代が変わるだけで、基準の端末が変わり、関門の合否が変わりうる（#81 の TBT 204 ms は、遅いマシンに当たったことも効いていた。ADR 0015 の追記）。

Lighthouse の文書（v12.6.1 の `docs/throttling.md`）によると、既定の 4 倍は「高性能なデスクトップ（benchmarkIndex 1,500〜2,000）で測ると、中位のスマートフォン（125〜800）のどこかになる」ように決めた倍率で、マシンの速さに合わせて倍率を変えることを勧めている。

測った結果から分かったことは 5 つある。

1. **LCP は CPU の倍率で動かない。** CI の LCP の中央値は、倍率 2 でも 8 でも 1,660〜1,691 ms だった。ラボの LCP は、遅い 4G の模擬で JS が届くまでの時間でほぼ決まっている（FCP は倍率によらず約 760 ms）。だから「CI の LCP を利用者の p75 に合わせる」やり方では、基準の端末は決まらない。
2. **LCP には山が 2 つある。** CI の 105 回のうち 78 回は 1,659〜1,670 ms、21 回（20%）は 2,167〜2,516 ms だった（残りの 6 回は 1,513〜1,812 ms）。高い山の値は手元の値と同じ並びで、倍率とともに少し増える（倍率 2 で約 2,170 ms、8 で約 2,450 ms）。どちらになるかは回ごとに変わり、マシンにも倍率にもよらない。Lighthouse が LCP を見積もるときに、どの JS までを「LCP の前に要るもの」に数えるかが、実際の描画と JS の読み込みの前後で変わるためと考えられる（未確認）。#85 の LCP 2,273 ms は、3 回のうち 2 回が高い山だった回にあたると考えられる。倍率の補正ではこの揺れは消えないが、高い山でも、基準の端末にあたる倍率（5〜6）では 2,258〜2,392 ms で、関門（2,500 ms）の内にある。
3. **TBT は倍率に強く反応し、「benchmarkIndex ÷ 倍率」が同じなら、CI のマシンが違っても同じ値になる。** 速さの違う 2 種類のマシン（benchmarkIndex 約 2,440 と約 3,120）で、「benchmarkIndex ÷ 倍率」が 500 のときの TBT は 196 / 199 / 197 ms、800 のときは 84 / 83 / 84 ms だった（上の 2 つ目の表）。決定 2 の補正は、CI のマシンの世代の違いを吸収できる。
4. **benchmarkIndex は、CI のマシンと手元のマシンの間では通用しない。** 「benchmarkIndex ÷ 倍率」が同じ約 600 でも、TBT は CI が約 150 ms、手元が 59 ms だった。基準の端末の数値は CI のマシンの単位で決め、手元の値は関門の判定に使わない（ADR 0023 決定 2 と同じ）。
5. **1 回の benchmarkIndex は、下に外れることがある。** Xeon のマシンでは、35 回のうち 4 回が中央値より 5% 以上小さく（最小は −21%）、そのときも TBT は変わらなかった（上には最大で +7%）。温める回でも、1 回目が 2 回目より 13% 小さいことがあった（2,109 と 2,419。そのときの 1 回目の TBT は 499 ms）。CI に残っている結果では、1 回目が 720〜1,970 に落ちることも多い（CI に残っている結果の 1）。補正に使う値を 1 回の測定から取ると、倍率が小さく（甘く）なりうる。

いまの `develop` の TBT が関門の 200 ms を超えるのは、「benchmarkIndex ÷ 倍率」が約 490 より小さいときだった。いまの CI の条件（約 2,440 ÷ 4 = 610）では 146〜157 ms で通るが、Lighthouse が既定の 4 倍で想定している端末（1,500〜2,000 ÷ 4 = 375〜500。中央は約 440）では 223〜245 ms になり、関門を超える。手元のレポートでは、TBT のほとんどは共有のチャンク 1 つ（Sentry と Next.js のクライアント側の処理を含む。転送量 78 kB）の実行で、内訳はまだ調べていない。

## 検討した選択肢

**揺れを減らすやり方**

| 案 | 良い点 | 悪い点 |
|---|---|---|
| A. いまのまま（3 回の中央値・倍率 4） | 変更がない | 1 回目の外れ値と、マシンの世代の違いで合否が変わる |
| B. 回数だけ増やす（5 回の中央値など） | 1 回目の外れ値に強くなる | マシンの世代の違いは残る。CI の時間が延びる |
| **C. 温める回を捨て、CPU の倍率をマシンの速さで補正して基準の端末を固定する** | 1 回目の外れ値と、マシンの世代の違いをどちらも取り除ける | 補正の仕組みを CI に足す。基準の端末の数値を決める必要がある。LCP の 2 つの山は残る |

**基準の端末（`B_ref`）の決め方**

| 案 | 良い点 | 悪い点 |
|---|---|---|
| ア. CI の LCP が、モバイルの利用者の LCP の p75 と同じになる端末（最初の案） | 基準が実際の利用者に直接結びつく | 決まらない。CI の LCP は倍率で動かない（測った結果の 1） |
| **イ. Lighthouse が既定の 4 倍で想定している端末（約 440）** | 関門の TBT 200 ms は、Lighthouse がこの条件に対して決めた「良い」の線（ADR 0023 決定 3）なので、測る条件と関門がそろう。実際の利用者の値を待たずに決まる | いまの `develop` が TBT の関門を超える。実際の利用者とは、あとから比べて確かめる形になる |
| ウ. いまの CI の条件（約 600）を固定する | いまの `develop` が通る | 「たまたま当たったマシン」を基準にするだけで、根拠がない。#81 の合否はきわどいまま（同じ条件で 204 ms だった） |

## 決定

1. **温める回を捨てる。** 測る前に、同じサーバーへ Lighthouse を 2 回走らせ、その結果は判定に使わない。判定は、そのあとの 3 回の中央値で行う（いまと同じ回数）。
2. **CPU の倍率を、マシンの速さで補正する。** 温める 2 回の benchmarkIndex の大きいほう（`B_ci`）から、`倍率 = B_ci ÷ B_ref` を計算し、3 回の測定に `throttling.cpuSlowdownMultiplier` として渡す。大きいほうを使うのは、benchmarkIndex が大きく外れるのは下だけのため（測った結果の 5）。回線の条件（遅い 4G）は変えない。
3. **基準の端末（`B_ref`）は 440 に固定する。** Lighthouse が既定の 4 倍で想定している端末（高性能なデスクトップ 1,500〜2,000 ÷ 4 = 375〜500 の中央）で、単位は CI のマシン（ubuntu-latest）の benchmarkIndex。実際の利用者の値は、`B_ref` を決めるのには使わず、確かめるのに使う。2026-10-05 以降に、PostHog の `web_vital`（ADR 0021）でモバイルの利用者の LCP と INP の p75 を見て、目標（ADR 0023 決定 1）を満たしていないのに CI が通っているなら、基準が甘いので新しい ADR で見直す（ADR 0023 決定 2 の「1 週間分たまったら見直す」をここで行う）。
4. **補正に使った値を PR に出す。** CI の結果のコメントの Lighthouse の表に、`B_ci` と倍率を足す（ADR 0023 決定 4 と同じ考え方で、判定の条件を読めるようにする）。
5. **関門の値（LCP 2,500 ms・TBT 200 ms・CLS 0.1・JS 350,000 B）は変えない。** 変えるのは、それを測る条件だけ。

## 結果

- 良い点: 関門の合否が、CI のマシンの当たり外れではなく、コードの変化で決まるようになる。測る条件が、関門の値を決めたときの前提（Lighthouse の中位のスマートフォン）とそろう。
- 悪い点: CI の Lighthouse が 2 回ぶん（1 分ほど）長くなる。補正の仕組みのコードが増える。LCP の 2 つの山による揺れは残る。
- あとで困ること: **この条件では、いまの `develop` が TBT の関門を超える**（背景の最後）。補正を入れると CI が赤になるので、関門を緩めるのではなく、先に `develop` の TBT を減らす（何を減らすかは別の ADR）。#81（Next.js 16）の判定は、そのあとになる。

## オーナーに確認したいこと

1. 書き直した決定 1〜3 でよいか（温める回を 2 回にして `B_ci` を大きいほうから取る。`B_ref` は 440 に固定し、実際の利用者の値は確かめるのに使う）。
2. `B_ref` を 440 にすると、いまの `develop` は TBT の関門を超える。進め方は次のどれにするか。
   - **(a) 先に `develop` の TBT を減らす**（新しい ADR。共有のチャンクの中身を調べるところから）。減らせたら、この ADR の補正を入れる。#81 はそのあとで判定する。関門も基準も緩めない（勧める案）。
   - (b) `B_ref` を、いまの CI の条件（約 600）にする。いまの `develop` は通るが、基準に根拠がなくなる。
   - (c) 補正の仕組みだけを先に入れ、TBT を減らすまで TBT の関門を警告に下げる。CI は赤くならないが、そのあいだ TBT が増えても止まらない。
