# 0025. CI の Lighthouse の基準の端末を固定し、温める 1 回を捨てる

- 状態: 提案（基準の端末の数値は、2026-10-05 以降の実際の利用者の値で埋める）
- オーナーの確認: 未
- 日付: 2026-10-02
- 関連: ADR 0006 / 0012 / 0015 / 0021 / 0023

## 背景

ADR 0023 決定 2 は、PR の時点の「基準の利用者」を Lighthouse の既定のモバイルの設定（遅い 4G・4 倍遅い CPU）にし、判定を CI の値で行うとした。実装してみると、CI の値が利用者の体験と関係のない理由で大きく揺れ、関門の合否がそれで決まりうることが分かった。

CI に残っている Lighthouse の結果から、アプリのコードが同じで文書だけが違う実行を 2 組（各 5 回の実行 × 3 回の測定）集めて調べた（2026-10-02）。

| 組 | コード | 1 回目 | 2・3 回目のマシンの速さ（benchmarkIndex） | 2・3 回目の LCP | 2・3 回目の TBT |
|---|---|---|---|---|---|
| A | ADR 0024 のあと | 5 回中 3 回で外れ値 | 2,342〜2,472 | 1,513〜2,273 ms（中央値 1,666） | 125〜178 ms |
| B | ADR 0005 のあと | 5 回中 5 回で外れ値 | 2,338〜2,487 | 1,815〜1,821 ms | 148〜193 ms |

分かったことは 3 つある。

1. **1 回目だけが大きく外れる。** 10 回の実行のうち 8 回で、1 回目の LCP が 2.5〜3.5 秒、TBT が 600〜2,700 ms になった。そのとき Lighthouse が測ったマシンの速さも 720〜1,970 に落ちている。起動したばかりのサーバーと Chrome が CPU を取り合っているためと考えられる。3 回の中央値で判定しているので多くは救われるが、残りの 2 回のどちらかもぶれると外れ値が選ばれる（#85 の LCP 2,273 ms）。
2. **2・3 回目は安定している。** B 組の LCP は 10 回とも 1,815〜1,821 ms だった。
3. **日によってマシンが変わる。** 2026-09-28 の実行ではマシンの速さが 4,150〜4,490 で、いまの倍近かった。そのころの `develop` の TBT は 58〜65 ms、いまは 150 ms 前後。Lighthouse の「4 倍遅い CPU」は測るマシンを基準にした倍率なので、GitHub のマシンの世代が変わるだけで、基準の端末が変わり、関門の合否が変わりうる（#81 の TBT 204 ms は、遅いマシンに当たったことも効いていた。ADR 0015 の追記）。

Lighthouse の文書によると、既定の 4 倍は「高性能なデスクトップ（benchmarkIndex 1,500〜2,000）で測ると、中位のスマートフォンになる」ように決めた倍率で、マシンの速さに合わせて倍率を変えることを勧めている。

## 検討した選択肢

| 案 | 良い点 | 悪い点 |
|---|---|---|
| A. いまのまま（3 回の中央値・倍率 4） | 変更がない | 1 回目の外れ値と、マシンの世代の違いで合否が変わる |
| B. 回数だけ増やす（5 回の中央値など） | 1 回目の外れ値に強くなる | マシンの世代の違いは残る。CI の時間が延びる |
| **C. 温める 1 回を捨て、CPU の倍率をマシンの速さで補正して基準の端末を固定する** | 揺れの 2 つの原因をどちらも取り除ける。基準の端末を「実際の利用者」に結びつけられる | 補正の仕組みを CI に足す。基準の端末の数値を決める必要がある |

## 決定

1. **温める 1 回を捨てる。** 測る前に、同じサーバーへ Lighthouse を 1 回走らせ、その結果は判定に使わない。判定は、そのあとの 3 回の中央値で行う（いまと同じ回数）。
2. **CPU の倍率を、マシンの速さで補正する。** 温める 1 回の結果の benchmarkIndex（`B_ci`）から、`倍率 = B_ci ÷ B_ref` を計算し、3 回の測定に `throttling.cpuSlowdownMultiplier` として渡す。`B_ref` は基準の端末の速さ（決定 3）。回線の条件（遅い 4G）は変えない。
3. **基準の端末（`B_ref`）は、実際の利用者の値から決める。** 2026-10-05 以降に、PostHog の `web_vital`（ADR 0021）で、モバイルの利用者の LCP の p75 を出す。`develop` の CI の LCP が、その値と同じになる `B_ref` を選ぶ。手順は次のとおり。
   1. 手元か CI で、`develop` を倍率を変えて測り、LCP と倍率の関係を出す。
   2. モバイルの p75 の LCP に合う倍率から `B_ref` を逆算する（`B_ref = 測ったマシンの benchmarkIndex ÷ 倍率`）。
   3. モバイルの件数が少なく p75 が決まらないときは、Lighthouse の定義の中位のスマートフォン（約 440。高性能なデスクトップの 1,750 ÷ 4）を仮に使い、件数がたまったら見直す。
4. **補正に使った値を PR に出す。** CI の結果のコメントの Lighthouse の表に、`B_ci` と倍率を足す（ADR 0023 決定 4 と同じ考え方で、判定の条件を読めるようにする）。
5. **関門の値（LCP 2,500 ms・TBT 200 ms・CLS 0.1・JS 350,000 B）は変えない。** 変えるのは、それを測る条件だけ。

## 結果

- 良い点: 関門の合否が、CI のマシンの当たり外れではなく、コードの変化で決まるようになる。基準の端末が実際の利用者に結びつく。
- 悪い点: CI の Lighthouse が 1 回ぶん（30 秒ほど）長くなる。補正の仕組みのコードが増える。
- あとで困りうること: 基準の端末を実際の利用者に合わせた結果、いまの `develop` が関門を超えることがありうる（手元で中位のスマートフォン相当に補正すると、LCP 2.6 秒・TBT 約 200 ms だった。ADR 0015 の追記）。そのときは、関門を緩めるのではなく、LCP が JS を待つ作り（注意事項のモーダル。ADR 0009）を先に直す順番を考える。

## オーナーに確認したいこと

1. 決定 1〜5 の進め方でよいか。
2. 基準の端末を「モバイルの利用者の LCP の p75 に合う端末」にすること（決定 3）でよいか。デスクトップの利用者のほうが多くても、遅いほうのモバイルに合わせる。

## 完了条件（DoD）

- [ ] CI の Lighthouse が、温める 1 回を捨ててから 3 回測っている
- [ ] CPU の倍率が `B_ci ÷ B_ref` で補正され、CI のコメントに `B_ci` と倍率が出る
- [ ] `B_ref` の値と、その根拠（モバイルの p75 の LCP、測った倍率と LCP）を追記に書いた
- [ ] 同じコードで 5 回 CI を走らせ、判定に使う LCP と TBT のばらつきが、この ADR の前より小さいことを確かめた（数値を追記に書く）
- [ ] ロードマップの共通 DoD を満たした
