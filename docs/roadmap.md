作業はフェーズ単位で進める。フェーズが終わるたびに `git diff` を自分の目で読み、フェーズの完了条件（DoD）を確かめてから次へ進む。

```
Phase 0  計画と運用の土台（コードなし）                    ← 完了
Phase 1  緊急の対応と、計測・品質ゲートの土台
Phase 2  基盤の整理（依存・Next.js 16・状態管理）

Phase 4  デザインと UI/UX・アクセシビリティ
Phase 5  国際化と SEO
Phase 6  効果の検証と次の計画
```

## 順番の考え方

1. **本番で利用者が困っていることを先に止める**（Phase 1 の hotfix）。
2. **変える前に測る。** アナリティクスとパフォーマンスのベースラインを Phase 1 で取り、Phase 6 で比べる。測る前に UI を変えると、良くなったかを判定できない。
3. **壊したら気づける状態にしてから変える。** CI が落ちても緑になる状態（Q-1）を Phase 1 で直す。
4. **土台を減らしてから積む。** 未使用の依存を消し（Phase 2）、Next.js 16 に上げてから、後続の ADR を新しい書き方で 1 回で実装する。
5. **見た目より中身を先に。** 結合の仕組みが変わると（Phase 3）、注意事項のモーダルが要らなくなるなど、UI の前提が変わる。Phase 4 の UI はその後に作る。
6. **i18n は文言が固まってから。** Phase 4 で文言が大きく変わるので、辞書に移すのはその後（Phase 5）。ただし Phase 4 の新しいコンポーネントは、文言を 1 箇所（定数）に寄せて書き、移しやすくしておく。
